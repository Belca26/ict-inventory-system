## 2. Layered request flow (every module follows this)

```
HTTP request
   │
   ▼
routes.ts        — defines the path + HTTP verb, chains middleware in order:
   │                 authenticate → authorize(roles) → validate(zodSchema) → controller
   ▼
controller.ts     — thin: pulls req.user/req.body/req.params into a plain
   │                 context object, calls the service, maps result → HTTP response.
   │                 No business logic lives here.
   ▼
service.ts        — ALL business logic: department-scoping enforcement,
   │                 cross-entity validation (e.g. spec must match asset
   │                 category), state transitions (maintenance COMPLETED →
   │                 asset ACTIVE), audit log writes, Prisma queries.
   ▼
Prisma Client → PostgreSQL
```

Why this shape: controllers stay swappable (could sit behind REST, or later a
GraphQL/tRPC layer, without touching business logic). Services are the only
layer that touches `prisma` directly — makes them independently testable
with a mocked Prisma client.

## 5. Cross-cutting concerns and where they live

| Concern | Where enforced |
|---|---|
| Authentication | `authenticate` middleware, every protected route |
| Authorization (role) | `authorize(...roles)` middleware, per-route |
| Authorization (department scope) | inside each **service**, not middleware — because it depends on which specific asset/record is targeted, not just the route |
| Input validation | `validate(zodSchema)` middleware, per-route, before controller ever runs |
| Audit logging | `writeAuditLog()` called explicitly inside services on create/update/delete |
| Soft deletes | `deletedAt` field on `User` and `Asset`; every query that should exclude deleted rows filters `deletedAt: null` explicitly (no global Prisma middleware — deliberate, so it's visible per-query rather than invisible magic) |
| Rate limiting | `express-rate-limit` on `/api/auth/login` only, for now — extend to other write-heavy endpoints if abuse is observed |
| Error handling | every controller catches into `next(err)` → single `errorHandler` middleware → consistent JSON error shape |

## 6. Data flow example: a maintenance job, start to finish

```
1. Technician: POST /api/maintenance  {assetId, maintenanceType: CORRECTIVE, status: PENDING}
   → asset.status flips to UNDER_MAINTENANCE

2. Technician: POST /api/maintenance/:id/procedures  {procedures: [Cleaning, RAM Upgrade]}
   Technician: POST /api/maintenance/:id/parts        {parts: [{partName: "8GB RAM stick"}]}
   Technician: POST /api/maintenance/:id/attachments  (multipart: before/after photos)

3. Technician: PATCH /api/maintenance/:id  {status: COMPLETED, timeFinished: ...}
   → labourHours auto-computed from timeStarted/timeFinished
   → asset.status reverts to ACTIVE

4. Technician: POST /api/maintenance/:id/signatures  {signatureImagePath: ...}
   → signerRole = ICT_TECHNICIAN

5. Department Rep: POST /api/maintenance/:id/signatures  {signatureImagePath: ...}
   → REJECTED if status !== COMPLETED
   → signerRole = DEPARTMENT_REPRESENTATIVE, confirms the work

6. Every step above writes an AuditLog row (who, what, old/new value, IP, timestamp)
```

## 7. Deployment topology

```
GitHub repo (monorepo or two repos: frontend / backend)
        │
        ├── frontend/  → Vercel (auto-deploy on push to main, preview deploys per PR)
        │
        └── backend/   → Railway (auto-deploy on push to main)
                              │
                              └── DATABASE_URL → Supabase Postgres (separate project,
                                                  not co-located with Railway)
```

Environment separation: use Railway's environment feature (or separate services)
for `staging` vs `production`, each pointing at its own Supabase project —
never point a staging backend at the production database.

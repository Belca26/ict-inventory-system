# Production Deployment Guide

## 1. Program structure and design (recap)

Two independent repositories, three managed services:

```
                    ┌─────────────────────────┐
   Browser  ───────▶│  ict-inventory-frontend  │  Vercel
                    │  React + Vite            │  (static build, CDN-served)
                    └────────────┬─────────────┘
                                 │ HTTPS, JSON, JWT in Authorization header
                                 ▼
                    ┌─────────────────────────┐
                    │  ict-inventory-system    │  Railway
                    │  Node.js + Express API   │  (long-running container)
                    └────────────┬─────────────┘
                                 │ Postgres wire protocol (pooled)
                                 ▼
                    ┌─────────────────────────┐
                    │  Supabase Postgres       │  Supabase
                    │  (managed database)      │
                    └─────────────────────────┘
```

**Design principles carried through every layer** (see `docs/ARCHITECTURE.md` for the full breakdown):
- **Asset-centric data model** — maintenance, specs, and history all hang off `Asset`, not the reverse.
- **Layered backend**: `routes → controller → service → Prisma`. Services own all business logic and are the only layer touching Prisma directly.
- **Department-scoping enforced in services**, not just route middleware — verified by an integration test (`tests/integration/asset-scoping.test.ts`), not just asserted in comments.
- **RBAC via middleware** (`authenticate` + `authorize(...roles)`), consistent across every module.
- **Audit logging** on every create/update/delete, written through one shared `writeAuditLog()` utility.

## 3. VS Code workspace setup

Since these are two separate repositories, open them as a **multi-root workspace** rather than two disconnected VS Code windows — you get cross-project search, one integrated terminal panel with two working directories, and shared extension recommendations.

**Folder layout on disk (suggested):**
```
ict-inventory/                      ← parent folder, not itself a git repo
├── ict-inventory-system/           ← git clone of the backend repo
├── ict-inventory-frontend/         ← git clone of the frontend repo
└── ict-inventory.code-workspace    ← the workspace file below
```

Create `ict-inventory.code-workspace` in the parent folder:

```json
{
  "folders": [
    { "name": "backend", "path": "ict-inventory-system" },
    { "name": "frontend", "path": "ict-inventory-frontend" }
  ],
  "settings": {
    "typescript.tsdk": "backend/node_modules/typescript/lib",
    "editor.formatOnSave": true,
    "editor.defaultFormatter": "esbenp.prettier-vscode",
    "files.exclude": {
      "**/node_modules": true,
      "**/dist": true
    }
  },
  "extensions": {
    "recommendations": [
      "prisma.prisma",
      "dbaeumer.vscode-eslint",
      "esbenp.prettier-vscode",
      "bradlc.vscode-tailwindcss",
      "orta.vscode-jest",
      "eamodio.gitlens",
      "ms-azuretools.vscode-docker"
    ]
  }
}
```

Open it with `File → Open Workspace from File…`, or from a terminal: `code ict-inventory.code-workspace`.

**Why each extension:** Prisma (schema syntax highlighting + autocomplete on `.prisma` files), Tailwind CSS IntelliSense (autocomplete for the custom token classes like `bg-brandMaroon`), Jest (inline pass/fail gutters on the test files you already have), Docker (manage the compose stack from the sidebar instead of the terminal), GitLens (blame/history — useful once this is a team codebase, not just solo).

Two integrated terminals, one per root, running side by side during development:
```bash
# terminal 1 (backend root)
docker compose up -d postgres
npm run dev

# terminal 2 (frontend root)
npm run dev
```

## 4. Pre-deployment checklist

Generate production secrets — **never reuse the dev/test placeholder values from `.env.example` or `docker-compose.yml`**:

```bash
# Cross-platform (Node is already a dependency, so this works on Windows too,
# unlike `openssl rand` which needs Git Bash or WSL):
node -e "console.log(require('crypto').randomBytes(48).toString('base64'))"
```

Run it twice — once for `JWT_ACCESS_SECRET`, once for `JWT_REFRESH_SECRET`. Store both in a password manager, not in any committed file.

## 5. Database — Supabase

1. Create a project at supabase.com (choose a region close to Kenya — `eu-west-1` or `eu-central-1` will generally have lower latency than US regions).
2. **Project Settings → Database → Connection string**. Supabase gives you two pooled connection strings:
   - **Session mode** (port 5432) — required for `prisma migrate deploy` (migrations need a session-level connection).
   - **Transaction mode** (port 6543) — use this one for the running app's `DATABASE_URL` in Railway (better for serverless-style connection churn; Railway's long-running container works fine with either, but transaction mode is the safer default under load).
3. Copy the **session mode** string, run migrations against it once (see step 6.4) — after that, the app itself uses the **transaction mode** string.

---

## 6. Backend — Railway

1. **New Project → Deploy from GitHub repo** → select `ict-inventory-system`.
2. Railway auto-detects Node via Nixpacks — no Dockerfile needed unless you prefer it (see `docs/DOCKER.md` for that path).
3. **Variables** tab — set:
   ```
   NODE_ENV=production
   DATABASE_URL=<Supabase transaction-mode string>
   JWT_ACCESS_SECRET=<generated>
   JWT_REFRESH_SECRET=<generated>
   JWT_ACCESS_EXPIRES_IN=15m
   JWT_REFRESH_EXPIRES_IN=7d
   CORS_ORIGIN=<your Vercel URL, set after step 7 — placeholder for now>
   SMTP_HOST=...        (or leave unset to log emails instead of sending)
   SMTP_PORT=587
   SMTP_USER=...
   SMTP_PASSWORD=...
   SMTP_FROM="ICT Inventory System <noreply@university.ac.ke>"
   ```
4. **Run the initial migration once**, from your local machine, pointed at the Supabase **session-mode** string (not from inside Railway — `migrate dev` needs an interactive-capable connection):
   ```bash
   DATABASE_URL="<session-mode string>" npx prisma migrate deploy
   DATABASE_URL="<session-mode string>" npx prisma db seed
   ```
5. **Settings → Networking → Generate Domain** to get the public Railway URL. Optionally attach a custom domain (e.g. `api.ictinventory.university.ac.ke`) via CNAME.
6. **Deploy**. Railway runs `npm install && npm run build && npm start` by default — confirm `package.json`'s `start` script (`node dist/server.js`) matches, which it does from Step 2 of the backend build.
7. Verify: `curl https://<railway-domain>/health` → `{"status":"ok"}`.
8. **Change the seeded admin password immediately** — log in as `admin@university.ac.ke` / `ChangeMe123!` via the API or frontend and call `POST /api/auth/change-password`.

**Uploads caveat, repeated because it matters at deploy time:** Railway's filesystem is ephemeral across redeploys. `uploads/maintenance/` will be wiped the next time you deploy. Fine for initial launch; before real usage, swap `upload.config.ts` for S3-compatible storage (Supabase Storage is the path of least resistance since you already have a Supabase project).

---

## 7. Frontend — Vercel

1. **New Project → Import Git Repository** → select `ict-inventory-frontend`.
2. Vercel auto-detects Vite. Confirm build settings:
   - Build command: `npm run build`
   - Output directory: `dist`
3. **Environment Variables**:
   ```
   VITE_API_URL=https://<your Railway domain>
   ```
4. Deploy. Vercel gives you a `*.vercel.app` URL immediately, plus automatic preview deployments on every PR.
5. **Go back to Railway** and set `CORS_ORIGIN` to this exact Vercel URL (or your custom domain once attached) — the placeholder from step 6.3 must be replaced or the frontend's requests will be blocked by CORS.
6. Attach a custom domain in Vercel's Domains tab if you have one (e.g. `inventory.university.ac.ke`).

## 8. Environment separation (staging vs. production)

Don't point a staging deployment at the production Supabase project. Minimum viable separation:
- A second Supabase project (`ict-inventory-staging`) — Supabase's free tier covers this.
- A second Railway environment or service, with its own `DATABASE_URL` pointed at the staging Supabase project.
- A second Vercel deployment (or just rely on Vercel's automatic PR preview deployments, which already point at whatever `VITE_API_URL` you configure per-environment in Vercel's dashboard).

## 9. Post-deploy verification checklist

- [ ] `GET /health` returns 200
- [ ] Login with the seeded admin account succeeds, then **password changed**
- [ ] `POST /api/users` (admin) creates a real ICT Technician and Department Representative account per your actual org
- [ ] Register one real asset end-to-end through the frontend
- [ ] Open a maintenance record, add a procedure, upload an attachment, mark it completed, sign as both technician and department rep
- [ ] `GET /api/export/assets?format=xlsx` downloads a working spreadsheet
- [ ] Confirm the cron log line appears in Railway logs the next day at 07:00: `[cron] Daily notification scan complete...`
- [ ] Confirm `Supabase → Database → Advisors` (or `get_advisors` if using the Supabase MCP tooling) shows no missing-RLS or security warnings — the app relies entirely on backend RBAC, so Supabase Row Level Security is intentionally not configured, but it's worth confirming direct DB access is otherwise locked down to the app's connection string only.

## 10. Rollback

- **Backend**: Railway keeps prior deployments — "Redeploy" any earlier build from the Deployments tab if a release breaks something. Database migrations are the one thing that doesn't auto-rollback: if a migration needs reverting, write a new forward migration that undoes it rather than trying to roll the schema back, since `prisma migrate deploy` is append-only by design.
- **Frontend**: Vercel's Deployments tab → "Promote to Production" on any previous build, instantly.
